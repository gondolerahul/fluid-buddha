# Launch record: FluidBuddha production on Azure, 26 November 2026

What was actually done to put FluidBuddha into production, what went wrong on the way and how it was fixed.
The plan is in [azure-production-plan.md](azure-production-plan.md), the owner's steps in
[azure-operator-guide.md](azure-operator-guide.md), day-to-day operation in [azure-runbook.md](azure-runbook.md).
Read this record before a rebuild, a second environment (staging, dev) or a move to another subscription: every
problem below will happen again in the same order unless its fix is in place.

## Problems and fixes

### 1. Exchange refused the mailbox-scope commands

`New-ManagementScope` and the others answered *"The command you tried to run isn't currently allowed in your
organization"*. Smaller tenants have Exchange customization switched off. **Fix:** `Enable-OrganizationCustomization`
once, wait up to an hour, run the commands again. Now in the operator guide, A4 step 6.

### 2. `Connect-ExchangeOnline` hung

The sign-in window opened behind other windows (Windows' WAM broker) and the command seemed to hang.
**Fix:** look for the window in the taskbar, or connect with `Connect-ExchangeOnline -DisableWAM` (browser
sign-in) or `-Device` (a code to enter at microsoft.com/devicelogin). Now in the operator guide.

### 3. `AllocationFailed` for Standard_B2as_v2

Central India had quota and offered the size, but had no capacity for it when the VM was created. **Fix:** delete
the half-created VM and its OS disk, provision again with `-VmSize Standard_B2s_v2` (same 2 vCPU / 8 GiB, Intel
instead of AMD). `main.bicep` and `provision.ps1` now default to B2s_v2, so a rebuild asks for what production runs.

### 4. `ResourceNotFound` for the new VM's identity

On the run that created the VM, the role assignments read the VM's identity before Azure had finished creating
it. **Fix:** a re-run succeeded; the template now takes a new VM's principal ID from the VM module's output
instead of reading the resource (PR #35, `core.bicep`).

### 5. Release failed at Azure login: `AADSTS700213`

*"No matching federated identity record found"*. The repository uses GitHub's **immutable OIDC subjects**, which
carry the owner and repository IDs (`repo:gondolerahul@158562688/fluid-buddha@1439640317:…`), not the plain
`repo:owner/name:…` the federated credentials expected. **Fix:** both federated credentials updated in place
with `az identity federated-credential update`, and the template changed to take the prefix as
`githubSubjectPrefix` (PR #36). To see the prefix for any repository:

```powershell
gh api repos/OWNER/REPO/actions/oidc/customization/sub
```

### 6. Google Cloud refused to create the service-account key

The organisation enforces `iam.disableServiceAccountKeyCreation`. **Fix:** an organisation admin overrode the
policy on this one project (Organization Policies → "Disable service account key creation" → Override → Off),
the key was created and stored in Key Vault with `az keyvault secret set --file`, and the downloaded copy deleted.
Afterwards the project goes back to **Inherit parent's policy**, so no further keys can be made. While the policy
blocks creation, nothing downloads: an empty Downloads folder means the key was never made. Retiring the key in
favour of keyless federation is plan item 6.5.

### 7. CI red on `main` before the first release

The console audit flagged a Next.js advisory, Sentry SDK 3.0 broke the backend's observability extra, and gitleaks
flagged a public GUID and an example brief. **Fix:** PR #35 (Next.js 16.4.6, `sentry-sdk>=2.73.0,<3`, a narrow
`.gitleaks.toml` allowlist). Release refuses to build a commit whose CI isn't green, so this blocks launches.
